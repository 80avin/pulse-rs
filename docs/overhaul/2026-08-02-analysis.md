# Pulse Overhaul — Codebase Analysis (2026-08-02)

> Produced by an orchestrated audit: 8 per-module analysis subagents + 2 independent verification subagents. All line numbers verified against the working tree at v0.5.0. The workspace builds clean (`cargo build --workspace`, 39s) and the 6 existing unit tests pass — but those tests exercise only the rule engine.

## 0. Executive summary

Pulse has a **sound core architecture** (single-writer DB actor, bounded tagger queue, cursor pagination, atomic batch upserts) buried under a large accumulation of **broken correctness, dead code, doc/code drift, duplicated UI, and a half-migrated frontend**. The two bugs the user reported are real and root-caused:

- **(a) "Save with note doesn't show in saved list"** — `toggleSaved` is a *toggle*, but the note-save UI passes through it. Editing/adding a note on an already-saved item **unsaves** it (`data.svelte.ts:265` flips `saved`, `ReaderView.svelte:46`/`MobileReader.svelte:121` pass through `toggleSaved`). Backend foot-gun: `toggle_saved` writes `note=NULL` whenever note is omitted (`lib.rs:609` + `actor.rs:371`), and notes can never be cleared (`note ?? item.note` at `data.svelte.ts:269`).
- **(b) "Category change flashes then reverts to All; 2nd click works"** — three un-awaited async filter setters fire concurrently on tab click (`MobileTimeline.svelte:133`); each snapshots the filter *before* the await and the last `get_items_page` response **wins** (`timeline.svelte.ts:44-57`). No request identity/epoch guard exists. On the 2nd click the filter has converged. Desktop `handleFilterChange` has the same race.

The single biggest systemic problem: **the frontend is in the middle of a half-finished v2 migration** (bits-ui + Tailwind v4, store decomposition) that shipped with race conditions, duplicated menus, no tests, and stale specs. The user-facing complaints (fake title bar, dual context menus, unergonomic nav, broken save/category) are all symptoms of that state.

**Highest-risk non-UI issue: XSS.** Feed-supplied HTML is sanitized by a regex that only strips *quoted* `on*` attributes (`utils.ts:1-6`) and rendered via `{@html}` (`ReaderView.svelte:139`) with `withGlobalTauri: true` and `csp: null` (`tauri.conf.json:13,22`) — a crafted RSS item can reach every application-defined Tauri command (delete sources, run syncs, read DB stats, exfiltrate settings).

**Severity distribution** (deduped across reports): 2 user-blockers (both confirmed), 3 additional blockers (Android share recovery dead; Reddit `.rss` share 404s then auto-disables the feed; `sync run --detach` is a no-op), ~35 major issues, ~60 minor.

## 2. The two reported user bugs — root causes (both CONFIRMED by verification)

### R1 — Save/note: toggle semantics + note-wipe foot-gun

Chain (all verified):
1. Note-save UIs call `toggleSaved(id, note)` — `ReaderView.svelte:46`, `MobileReader.svelte:121`.
2. `data.svelte.ts:265` `item.saved = !item.saved` — a toggle. On an **already-saved** item, adding/editing a note **unsaves** it.
3. `data.svelte.ts:269` sends `{ id, saved: <flipped>, note: note ?? item.note }` → backend writes `is_saved=false` → item leaves the Saved list (and `data.svelte.ts:275` splices it out immediately in the saved filter).
4. Backend foot-gun: `PulseCore::toggle_saved` (`lib.rs:603-610`) wraps `note` as `Some(note)`, so omission → `Some(None)` → `actor.rs:371-379` binds SQL `NULL` → **wipes any existing note**.
5. Notes can never be cleared: empty draft → `undefined` → `undefined ?? item.note` **re-sends the old note**.

**Fix direction:** split "save/unsave" from "set note" into distinct operations; make the note field optional-with-unchanged semantics (`Option<Option<String>>` already encodes this — just don't force `Some(note)`); fix the eviction-on-state-change so the open item doesn't vanish from the reader (I-9).

### R2 — Category-change race: concurrent, un-sequenced timeline fetches

Chain (all verified):
1. `MobileTimeline.svelte:133` fires `setReadFilter(null)`, `setSavedFilter(null)`, `setGroupFilter(...)` — three fire-and-forget async setters.
2. Each setter → `resetAndFetch()` (`timeline.svelte.ts:44-57`), which snapshots the filter **synchronously** then `await`s `get_items_page` and `items.splice(...)`.
3. The three requests snapshot *different* filters (old group/All vs new group). **Last response wins.** If an All-page lands after the group page → list reverts. Second click: all three snapshot the same new filter → converges.
4. Amplifiers: desktop `handleFilterChange` fires two concurrent setters (`DesktopShell.svelte:141-149`); auto-fill `fetchNextPage` (`TimelineList.svelte:60-69`) can append an old-filter page-2 onto a new-filter page-1; `items.splice(findIndex,1)` with `findIndex==-1` **removes the last element** (`data.svelte.ts:248,275`).

**Fix direction:** single `applyFilter()` entry point (one request), plus a request epoch/generation counter so stale responses are discarded; guard `fetchNextPage` with the same epoch; make eviction a no-op when the item isn't in the list.

## 6. What this means for the overhaul

The architecture skeleton is worth keeping: the DB writer actor, bounded tagger queue, cursor pagination, atomic upserts, the IPC boundary, and the AI layer's separation are all sound foundations. The problems are concentrated in (1) correctness bugs in the backend's edges (scheduler, adapters, migrations, note semantics), (2) a half-finished, untested frontend with race conditions and duplicated UI, and (3) a large dead-code/doc-drift debt.

The overhaul should therefore be: **stabilize and harden the core, then rebuild the frontend shell and interaction model on a coherent design system, then add the roadmap features on top** — not a greenfield rewrite of the whole application.
